How much coincidence of wants is inside a Base block?

Before simulating APEX, measure the one thing only a batcher can capture: opposite trades in the same block that could cross without touching a pool. Methodology, three worked real-block examples, and the scan plan — for greenlight.

Why measure this first

An in-sequencer batcher sees the same pools, the same tokens, and the same orders as Fynd does per-order. Its only structural edge is internalization: when user A sells what user B is buying in the same block, the batch can cross them at one clearing price and skip the AMM round trip — its fee, its price impact, and one leg of gas. Everything else APEX might win on, Fynd already delivers.

So the coincidence-of-wants density of real Base blocks is the ceiling on batching's unique value. If the ceiling is low, the APEX simulation is measuring noise; if high, this same data tells us where (pairs, venues, block windows) the value concentrates. The day-0 numbers above say: thin at 2-second granularity (0.4–2% of volume), so the batching-window sweep is a first-class dimension, not a sensitivity check.

Data & the two traps the examples exposed

Source: base.dex.aggregator_trades (Allium) — solver/venue-routed flow, one row per decoded trade, with block_number, token amounts, and USD values. No chain access needed; the whole scan is SQL + local compute. This is the same trade universe hindsight decodes and the APEX replay would batch, so the numbers compose.

Testing the naive query on real blocks immediately surfaced two traps that define the methodology:

Trap 1 — multi-hop rows fabricate rings. The "largest 3-ring of the day" (block 49335445: SOL→USDC→cbBTC→SOL, $789) dissolved on inspection: cbBTC→SOL and SOL→USDC were two rows of one user's multi-hop route (same tx 0x0eab3dc5…, KyberSwap hop + a 1inch-LOP hop). Rows must be netted per transaction into user intents first, or routing internals masquerade as matchable demand.
Trap 2 — same-tx opposites are already-captured CoW. The "perfect" WETH/USDC match in block 49325116 ($19.2k vs $19.2k) is one CoW-protocol settlement filling a user order against a 1inch limit order — both legs share tx 0x8ccb7287…. That internalization already happened. The sequencer's incremental opportunity is only cross-transaction matches.

Intent extraction v2 (fixes both — and the trap the v1 fix created)

Trap 3 — found in self-review: uniform per-tx netting mangles batch settlements. A CoW-protocol settlement carries multiple user orders in one tx (3.8% of settlements); per-tx netting merges distinct users into one fake intent — or nets two users' opposite orders into nothing, silently deleting exactly the flow this study cares most about. ERC-4337 bundler txs bundle unrelated users the same way.
  1. Protocol-aware granularity. cow_protocol and uniswap_x rows are order-level by construction (verified: one row per CoW Trade event) — each row is one intent. In those txs, other rows (e.g. a 1inch-LOP fill inside a CoW settlement) are the solver's liquidity legs, not intents. All other (router) flow: net per transaction.
  2. Net in token units, not USD. Hop legs cancel exactly in token amounts; a single NULL-usd_amount row would break USD-based cancellation and mis-net the tx. USD enters only at valuation; txs with unvaluable legs are counted, never silently dropped.
  3. Canonicalize ETH ≡ WETH before matching — wrapping is free to a batcher, so a native-ETH sell matches a WETH buy. Stables are not merged (USDC/USDbC/DAI carry real spread).
  4. Keep txs netting to one sold + one bought token → one intent. Split routes collapse correctly (verified: a 2×$20k dual-aggregator split netted to one $40k intent). Multi-token txs: excluded and counted.
  5. Matching is computed across intents only (cross-tx for router flow; cross-order for batch settlements — two orders already crossed inside one settlement are realized, not potential).
  6. Same-sender guard: matches where both sides share sender_address (MM rebalancing, arb loops) are not user-value CoW — headline excludes them, reported separately.

Hindsight's netting philosophy transplanted: decline ambiguity, count what you drop, never record a wrong intent.

Metrics

Per block (and per multi-block window), over the netted intents:

W = Σ intent USD # addressable volume
pairwise_matched = Σ over pairs 2·min(flow_A→B, flow_B→A)
multilateral_cap = W − ½·Σ over tokens |net_demand_t| # rings & chains included
  • Pairwise matched volume — trade volume internalizable by direct A↔B crossing. Exact, conservative, and the number closest to what a simple in-sequencer matcher could capture.
  • Multilateral cap — what a full batch auction with uniform clearing prices could internalize: only each token's net demand must touch AMMs. Crucially, this bound already contains route-mediated netting (below), because re-routing an order never changes any token's endpoint imbalance.
  • Crossing surplus (pairwise, empirical) — no AMM model needed: both sides' executed prices are in the data. If sellers received p_sell (quote per base) and buyers paid p_buy, crossing at any price between them yields total surplus
    surplus = matched_base_qty × max(0, p_buy − p_sell)
    computed in token units, valued in USD, floored at zero — a negative gap (intra-block price move) means crossing helps no one; the negative-gap share is reported as its own statistic, not silently clipped.
  • Window sweep — every metric at tumbling (non-overlapping) windows of 1, 5, 15, 30, 150 blocks (2 s → 5 min). CoW density grows superlinearly with window; this chart is the report's centerpiece and directly answers "what if the batch waited?"
  • Splits — by pair tier (bluechip / stable / long-tail), by venue/project, by maker-involvement (intents whose tx contains RFQ/LOP maker fills — 1inch_lop, bebop_rfq, native_rfq — matchable liquidity but not retail demand), and by same-sender (excluded from headline).

Decomposing the cap: direct, rings, and route-mediated ("synthetic") CoW

A batch with uniform clearing prices can net more than opposite endpoint pairs. An order's route legs can oppose other orders: with order 1 USDC→WETH and order 2 PEPE→USDC where PEPE/USDC is thin but PEPE/WETH is deep, the batch routes order 2 as PEPE→WETH→USDC — its WETH→USDC leg crosses order 1 peer-to-peer, the thin pool is never touched, and only the deep pool absorbs the residual. This synthetic CoW by route choice is unique to batch settlement, and it is why the multilateral cap — not the pairwise number — is the true ceiling.

The scan decomposes the multilateral cap into three labeled buckets:

multilateral_cap = pairwise_direct + ring_attributable + route_mediated_residual
  1. Pairwise direct — as above, with exact empirical surplus.
  2. Ring-attributable — after removing pairwise-matched flow, greedy cycle cancellation on the residual intent-flow graph (3- and 4-cycles, min-edge cancelling). Ring surplus from the price product around the cycle: ring_qty × max(0, 1 − Π p_leg). Flow decomposition is greedy and non-unique — stated, not hidden.
  3. Route-mediated residual — the remainder: netting achievable only by choosing routes through shared tokens. Its volume is exact (it is a difference of exact quantities); its surplus is valued per netted token-unit by a per-token empirical AMM-cost proxy measured from this same dataset (the distribution of pairwise execution-price gaps per token tier — netted long-tail flow is worth ~100× netted bluechip flow). Labeled proxy, never mixed with exact numbers. The realizable value of this bucket is exactly what the APEX simulation phase prices later — Phase 0 sizes the bucket, APEX prices it.

Three real examples, worked

All from the last 24 h of Base, found by the netted cross-tx query. They span the three regimes the full scan will quantify.

Example 1 · bluechip, tight — block 49357908

WETH ↔ USDC, one seller vs one buyer, 2.9 bps apart

tx 0xe3f65364… (0x Settler)  sells 6.9168 WETH → 12,993.94 USDC ⇒ receives 1,878.61 USDC/WETH
tx 0x06f898db… (CoW)       buys 1.5187 WETH for 2,853.84 USDC ⇒ pays 1,879.15 USDC/WETH
Matched: 1.5187 WETH ($2,857 · the buyer fills fully; seller partially). Surplus cap: 1.5187 × (1,879.15 − 1,878.61) = $0.82 total (~2.9 bps round trip). Bluechip execution on Base is already tight — CoW saves almost nothing on majors. This honesty matters: most matchable volume lives here, most matchable value does not.
Example 2 · thin stable — block 49334803

msUSD ↔ USDC, split-route buyer vs single seller, 26 bps apart

tx 0xbe0c9b5a… (0x + Kyber split route)  buys 52,080.6 msUSD for 40,000 USDC ⇒ pays 0.76804 USDC/msUSD
tx 0x310c73eb… (KyberSwap)           sells 20,000 msUSD → 15,320.68 USDC ⇒ receives 0.76603 USDC/msUSD
Matched: 20,000 msUSD (~$15.3k). Surplus cap: 20,000 × 0.00201 = $40 (~26 bps). Note the netting at work: the buyer's two same-tx rows (dual-aggregator split) collapsed into one $40k intent instead of two. Thin-liquidity stables are the sweet middle: real volume, real spread.
Example 3 · dislocated long tail — block 49340445

VANA ↔ USDC, one $60k dump vs three opposite fills, 29% apart

tx 0x90e17926… (KyberSwap)  sells 106,722.5 VANA → 60,061.92 USDC ⇒ receives 0.5628 USDC/VANA
tx 0xffa9a9f8…, 0xec49da3e…, 0xbae740ad… (1inch LOP fills)
  together buy 22,756.1 VANA for 18,052.38 USDC ⇒ pay 0.7933 USDC/VANA
Matched: 22,756 VANA (~$18.0k). Surplus cap: 22,756 × (0.7933 − 0.5628) = $5,246 (~29%). A thin-liquidity dump crushed the seller's execution while opposite limit orders sat 29% higher in the same block. Caveats owned: the gap partly reflects intra-block price movement and the buyers are maker fills (tagged as such in the scan) — but this is exactly the dislocation a uniform-clearing-price batch monetizes for its users. The long tail is where CoW value concentrates.

The full scan

Tooling: Python + Polars, not Rust

Data arrives via ~7 per-day Allium extraction queries (intent-level rows: block, tx, sold, bought, USD, protocol tags — ~105k rows/day, ~13 MB/day). All matching math is dataframe group-bys over ≤1M rows — seconds in Polars. Rust buys nothing here; Python buys iteration speed and the plotting for the report. The script is rerunnable and window-parameterized; if this graduates into a recurring monitor, the logic ports into hindsight later.

Pipeline

  1. Extract — per-day SQL (the netting CTEs above) → intent parquet files, plus excluded-tx counters.
  2. Match — per window (1/5/15/30/150 blocks): pairwise matched volume + exact crossing surplus per pair; multilateral cap per window; maker/venue/pair-tier splits.
  3. Report — self-contained HTML: window-sweep curves, per-pair league table, surplus distribution (p50/p90/max), share of blocks with any match, and the day-0-style headline numbers over the full week.

Known limitations, owned upfront

  • Theoretical cap, not achievable capture. "Everyone participates, no limit prices bind, at one clearing price." Real capture is strictly below; the APEX simulation is what measures the achievable fraction. This analysis bounds whether that simulation is worth building.
  • Aggregator flow only. Direct DEX-router users (no aggregator) are additional matchable demand not counted here — the cap understates "everyone" in that direction. A follow-up can add single-swap direct-router txs from dex.trades.
  • USD netting tolerance. Netting uses Allium's usd_amount (99%+ populated); matching/surplus math is done in token units and only valued in USD, so price-column noise cannot fabricate matches.
  • Maker fills are matchable liquidity, not retail demand. LOP/RFQ-involved intents are tagged and reported as a separate slice, never silently mixed.
  • Volatility inflates dislocation surplus. Example-3-style gaps partly reflect intra-block moves. The per-pair surplus distribution is reported with medians, not just sums, so one VANA doesn't write the headline.
  • Base has no public mempool — settled per-block composition is the actual matching opportunity a sequencer sees; no MEV-reordering correction needed. (This cuts in our favor: the measure is clean.)
  • odos_v2 is stale in Allium since 07-28 (indexer gap, both chains) — a small known undercount, footnoted in the report.

  • Scope: 7 days of base.dex.aggregator_trades, tumbling-window sweep 1/5/15/30/150 blocks, maker/venue/pair-tier/sender splits.
  • Tooling: Python + Polars locally, Allium Explorer API extraction, self-contained HTML report.
